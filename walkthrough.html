0 · What is I3C, and what is this driver?

Before any code: a 60-second mental model so the rest makes sense.

Imagine a school classroom. The master is the teacher. The slaves (also called targets) are students. They all share two wires running across the room: one wire carries a clock tick (SCL), the other carries data (SDA). The teacher decides who speaks and when. I3C is the set of rules for how the teacher and students talk over those two wires — it's the modern, faster successor to the old I2C bus, and it's backward-compatible so old I2C students can still sit in the same class.

Some vocabulary you'll keep seeing:

TermPlain meaning
Master / ControllerThe chip that runs the bus. Here it lives inside the SAMA7D65 SoC. This driver controls the master.
Slave / TargetA sensor, EEPROM, etc. that answers the master.
SCL / SDAThe two physical wires: clock and data.
Dynamic AddressI3C lets the master assign each slave an address at boot instead of hard-coding it. The hand-out ceremony is called DAA.
CCCCommon Command Code — a standard "broadcast or directed" command the master sends (e.g. "everyone, reset your address").
IBIIn-Band Interrupt — a slave raising its hand to interrupt the master ("I have data!") without a separate interrupt wire.
HCIHost Controller Interface — a standardized register layout defined by MIPI so one driver can run many vendors' I3C hardware. This whole driver implements HCI.
Why does a "standard register layout" matter? Normally every chip vendor invents its own registers, so every chip needs its own driver. MIPI HCI says: "all compliant hardware exposes the same registers in the same places, and advertises its own capabilities in a version register." So core.c can read a version number and a capabilities word, then auto-pick the right behaviour. Vendor differences that don't fit the standard are handled by small quirks — which is exactly where the Microchip work lives.

1 · The big picture — how the files fit together

The driver is deliberately split into layers that plug into each other through function-pointer tables (vtables). The reason: the hardware comes in several versions and two transfer styles, and the authors wanted to add a new variant by dropping in a new file, not by sprinkling if (version==...) everywhere.

Think of a restaurant. core.c is the manager — it talks to the customer (the kernel's I3C subsystem) and delegates real work. Two things are swappable:
  • How food reaches the table → the transfer engine: either a waiter carrying plates by hand (PIO = CPU copies data) or a conveyor belt (DMA = hardware moves data). Same job, two implementations of the same hci_io_ops menu.
  • How orders are written down → the command model: old short notepad (cmd_v1, 32-bit descriptors) or new long notepad (cmd_v2, 64-bit descriptors), both implementing hci_cmd_ops.
The manager reads the hardware's version at boot and hires the right waiter and the right notepad. The Microchip board adds a couple of quirks — small house rules the manager applies for this specific kitchen.

2 · The boot journey: from probe to detecting a slave

Click any step to expand it. This is the exact path the code takes, top to bottom, the moment the kernel finds the I3C hardware described in the device tree.

1Kernel matches the device tree node to this driver
i3c_hci_of_match[] → i3c_hci_probe()
The device tree (sama7d65.dtsi) has a node i3c@e9000000 with compatible = "microchip,sama7d65-i3c-hci". At boot the kernel scans for a driver whose match table contains that string. Ours does — see the second entry of i3c_hci_of_match[] — so the kernel calls i3c_hci_probe(). Crucially, that match entry carries .data = a bitmask of quirks: PIO_MODE | CLK_SUPPORT | MCHP_RESP_BUF_THLD. That bitmask is how the rest of the driver later knows "this is the Microchip variant."
2Allocate state, map registers, fetch the quirk bitmask
i3c_hci_probe() — alloc, ioremap, device_get_match_data()
We devm_kzalloc the big struct i3c_hci (the driver's whole brain, defined in hci.h). We map the hardware's registers into CPU-accessible memory with devm_platform_ioremap_resource() → that pointer becomes hci->base_regs, the base every register access is relative to. Then hci->quirks = device_get_match_data() pulls in that bitmask from step 1.
The devm_ prefix means "device-managed": the kernel auto-frees these when the device goes away, so there's no manual cleanup path to get wrong.
3Microchip-only: grab the two clocks
if (quirks & HCI_QUIRK_CLK_SUPPORT) devm_clk_get_enabled("pclk"/"gclk")
Standard/AMD parts have one clock. The Microchip IP needs two: pclk (the peripheral/bus clock that makes the registers respond) and gclk (the generic/core clock, 125 MHz, whose rate later drives the SCL timing math). devm_clk_get_enabled() both fetches and turns them on. This block is gated behind the CLK_SUPPORT quirk so non-Microchip boards never look for clocks that don't exist in their device tree.
4Read the hardware's identity & capabilities
i3c_hci_init() — HCI_VERSION, HC_CAPABILITIES, table offsets
Now we interrogate the silicon. Read HCI_VERSION → major/minor/revision (e.g. v1.0). Read HC_CAPABILITIES → a word of feature flags. Read the "section" registers to learn where inside the MMIO window the sub-blocks live: the Device Address Table (DAT), Device Characteristics Table (DCT), the Ring Headers (DMA), the PIO block, and the Extended Capabilities list. Each offset is stored as a pointer like hci->DAT_regs.
This is the "self-advertising" magic of HCI — the driver doesn't hard-code addresses, it asks the chip where everything is.
5Walk the extended-capabilities list
i3c_hci_parse_ext_caps() → ext_caps.c
The hardware exposes a linked list of optional-feature blocks in MMIO. We walk it node by node (id + length header, then jump length*4 bytes to the next). Each known id has a parser that records useful pointers (debug regs, auto-command regs) or sets a quirk (e.g. NXP parts need RAW_CCC). See the ext_caps.c section.
6Pick the command model: cmd_v1 vs cmd_v2
switch(FIELD_GET(HC_CAP_CMD_SIZE, caps))
One bitfield in the capabilities word says whether descriptors are 32-bit (cmd_v1) or 64-bit (cmd_v2). We point hci->cmd at the matching vtable. From now on, code says hci->cmd->prep_i3c_xfer(...) and neither knows nor cares which version it is.
Microchip's IP is HCI v1.x → it uses cmd_v1 and the DAT/DCT v1 tables.
7Microchip-only: force PIO mode
if (quirks & HCI_QUIRK_PIO_MODE) hci->RHS_regs = NULL;
The next step auto-selects DMA if Ring Headers (RHS_regs) exist, else PIO. By nulling the ring-header pointer, we force the driver down the PIO path. The Microchip bring-up uses PIO (simpler, no DMA ring setup), so this quirk guarantees it even if the hardware advertises rings.
8Software reset & choose the transfer engine
i3c_hci_reset_and_init() → set hci->io = &mipi_i3c_hci_pio
Pulse SOFT_RST and wait for it to self-clear (clean slate). Set the data-endianness bit to match the CPU. Then: if RHS_regs is set → DMA, else if PIO_regs is set → PIO. We land on PIO (step 7), so hci->io = &mipi_i3c_hci_pio. Every later transfer goes through hci->io->.... (AMD's OD_PP_TIMING quirk would also run here — Microchip's timing runs later, in bus_init.)
9Request the interrupt, enable runtime PM, register with the I3C core
devm_request_irq() → i3c_master_register()
Hook up i3c_hci_irq_handler() (shared IRQ). Then the pivotal call: i3c_master_register() hands our i3c_hci_ops callback table to the kernel's generic I3C subsystem and says "I'm a master, here's how to drive me."
Up to now we only set ourselves up. i3c_master_register() is where we join the kernel's I3C world — and the kernel immediately calls us back to actually start the bus.
10The core calls us back: bring the bus to life
i3c_hci_ops.bus_init → i3c_hci_bus_init()
The I3C core now drives us. bus_init:
  • initialises the DAT (the seating chart) for cmd_v1;
  • asks the core for a free address and programs it as the master's own dynamic address;
  • calls hci->io->init() to set up PIO FIFOs;
  • Microchip quirks fire here: mchp_cfg_resp_buf_thld() (response-buffer threshold) and mchp_cfg_od_pp_timing() (compute SCL high/low counts from the 125 MHz gclk);
  • finally sets HC_CONTROL_BUS_ENABLE — the bus is now electrically live.
The timing quirk must be here, not in probe: the SCL rate it divides by is only populated by the core after registration, just before bus_init.
11Dynamic Address Assignment — the slaves get discovered
i3c_hci_ops.do_daa → i3c_hci_daa → hci->cmd->perform_daa → hci_cmd_v1_daa()
The core triggers DAA. Our code loops: grab a free address, broadcast an ENTDAA CCC, and the hardware clocks out each responding slave's 48-bit Provisional ID / BCR / DCR into the DCT. For every slave that answers we read its DCT entry, assign it the address, and tell the core via i3c_master_add_i3c_dev_locked(). When no one answers, DAA ends. This is the moment a slave is "detected." Full detail in the next section.
12Per-device attach & steady state
attach_i3c_dev / reattach_i3c_dev → driver probe for each slave
For each discovered slave the core calls attach_i3c_dev, where we allocate a DAT slot and write the slave's address into it. The slave's own kernel driver then probes. From here the bus is in steady state: reads/writes flow through i3c_xfers/i2c_xfers, and slaves can raise IBIs to get attention. All of these are callbacks in the 17-callback table.

3 · DAA, explained slowly

Dynamic Address Assignment is the heart of "slave detection." It deserves its own section because it's the one part that feels like magic.

The roll-call analogy. The teacher (master) doesn't have a class list. So on day one she says to the whole room: "Everyone who needs an address, get ready." (that's the ENTDAA broadcast). Then she says "Whoever has the lowest ID number, speak first." Each student is wearing a unique 48-bit badge (their Provisional ID). The hardware uses those badges to make exactly one student win each round — the rest stay quiet. The winner shouts their badge, the teacher writes it in the guest book (DCT) and hands them a desk number (dynamic address). Repeat until nobody answers. Now the teacher has a full class list.

What the code actually does — hci_cmd_v1_daa() in cmd_v1.c

#StepWhy
1Reset the DCT read index (mipi_i3c_hci_dct_index_reset)The guest book pointer goes back to page 0.
2Allocate a DAT entry & ask the core for the next free addressWe need a desk number ready to hand out before each round.
3Build an ENTDAA address-assignment command and queue itThis is the "everyone get ready, lowest ID speaks" broadcast.
4Hardware arbitrates; one slave wins and streams its 48-bit PID+BCR+DCR into the DCTThe wire-level magic — collision resolution happens in silicon, bit by bit.
5Read that DCT entry (dct_v1.c → PID, BCR, DCR)Identify who just answered.
6i3c_master_add_i3c_dev_locked(addr)Tell the kernel "a new device exists at this address" → triggers attach + its driver.
7Loop back to step 2 until the response says "no more devices"Keep handing out desks until the room is silent.
BCR / DCR / PID — the badge contents. PID = 48-bit Provisional ID, globally unique-ish (vendor + part + instance). BCR = Bus Characteristics Register: what the device can do on the bus (max speed, supports IBI?, etc.). DCR = Device Characteristics Register: what kind of device it is (a code meaning "accelerometer", "EEPROM", …). The kernel uses these to match the right slave driver.
cmd_v2 does DAA differently. In hci_cmd_v2_daa() the 8 bytes of ID come back as read data of the command itself (no separate DCT walk). Same outcome, different plumbing — a good example of why the vtable split exists.

core.c — the manager

Probe, lifetime, version detection, power management

drivers/i3c/master/mipi-i3c-hci/core.c

Everything that isn't a swappable strategy lives here. Its jobs:

  • Probe / remove — i3c_hci_probe() (walked through in section 2) and i3c_hci_remove() which just unregisters.
  • Version & capability detection — i3c_hci_init() reads the version/caps registers and chooses cmd_v1 vs cmd_v2 and PIO vs DMA.
  • Reset — i3c_hci_software_reset() and i3c_hci_reset_and_init().
  • The IRQ top-half — i3c_hci_irq_handler(): reads INTR_STATUS, handles core-level errors, then delegates to hci->io->irq_handler() (PIO or DMA).
  • The transfer plumbing — i3c_hci_process_xfer(): queue a transfer, wait for completion, and on timeout dequeue/abort it.
  • The 17 callbacks the I3C subsystem calls — the i3c_hci_ops table (next section).
  • Power management — runtime suspend/resume, including the Microchip dual-clock gating.

How a transfer flows through core.c

The order-taking pipeline. A higher layer (CCC, i3c_xfers, i2c_xfers) builds one or more struct hci_xfer "order tickets," asks hci->cmd->prep_* to fill in the descriptor words, marks the last ticket with ROC/TOC ("respond on completion"/"terminate on completion"), then hands the batch to i3c_hci_process_xfer(). That queues them via the engine, sleeps until the engine signals "done," and reads back the response status.
/* the universal "do this batch and wait" helper (simplified) */
int i3c_hci_process_xfer(hci, xfer, n){
    hci->io->queue_xfer(hci, xfer, n);          // PIO or DMA hands it to HW
    if (!wait_for_completion_timeout(done, t))  // sleep until IRQ wakes us
        hci->io->dequeue_xfer(hci, xfer, n);     // timed out → abort & reclaim
    if (RESP_STATUS(xfer[i].response))           // any error code?
        return hci->io->handle_error(hci, xfer, n);
}

Power management & the Microchip clocks

i3c_hci_rpm_suspend() disables the bus, suspends the engine, then (Microchip only) gates gclk then pclk. i3c_hci_rpm_resume() re-inits, (Microchip only) re-enables pclk then gclk, recomputes SCL timing, restores the master address and DAT, and re-enables the bus.

pio.c — the waiter who carries plates by hand

CPU-driven transfers via FIFO queues

drivers/i3c/master/mipi-i3c-hci/pio.c · implements mipi_i3c_hci_pio
PIO = Programmed I/O. The CPU does the carrying. To send a command, the CPU writes words into a hardware FIFO (a queue) one at a time. To get data back, the CPU reads words out of another FIFO. When a FIFO has room or has data waiting, the hardware raises an interrupt and the CPU does the next chunk. Simple, no setup — but the CPU is busy during transfers. This is the path the Microchip board uses.

The four FIFOs (hardware queues)

FIFODirectionCarries
COMMAND_QUEUE_PORTCPU → HWCommand descriptor words ("the order")
RESPONSE_QUEUE_PORTHW → CPUOne response word per command (status + length)
XFER_DATA_PORTbothThe actual payload bytes (TX out / RX in)
IBI_PORTHW → CPUIBI status + payload when a slave raises its hand

Key functions

FunctionRole
hci_pio_initRead FIFO sizes, set queue/data thresholds (when to interrupt), allocate the PIO bookkeeping struct.
hci_pio_queue_xferPush command words into the CMD FIFO; remember the xfer chain so the IRQ handler can find them.
hci_pio_irq_handlerThe workhorse. On each interrupt it services whichever condition fired: room to push more TX, RX data ready, a response arrived, or an IBI.
hci_pio_dequeue_xferAbort/reclaim a transfer that timed out.
hci_pio_process_ibi + request/free/recycleThe IBI machinery for the PIO path.

Threshold registers — "wake me when…"

PIO_QUEUE_THLD_CTRL and PIO_DATA_BUFFER_THLD_CTRL tell the hardware how full/empty a FIFO must get before it bothers the CPU with an interrupt. Set them too aggressively and you get interrupt storms; too lazily and you waste FIFO space. The interrupt-status bits the handler checks include STAT_RESP_READY, STAT_TX_THLD, and STAT_RX_THLD.

Microchip connection: the mchp_cfg_resp_buf_thld() quirk zeroes the response-buffer threshold field so the controller raises "response ready" after a single response (n+1 = 1) rather than waiting to batch several — important for the small, latency-sensitive transfers during bring-up.

dma.c — the conveyor belt

Hardware moves data via ring descriptors

drivers/i3c/master/mipi-i3c-hci/dma.c · implements mipi_i3c_hci_dma
DMA = Direct Memory Access. Instead of the CPU carrying every word, the driver sets up rings (circular arrays) of descriptors in RAM. Each descriptor says "here's a command, and here's the memory address for its data." The driver bumps an "enqueue pointer," and dedicated hardware reads the descriptors, moves the data to/from RAM itself, and bumps a "dequeue pointer" when done. The CPU only gets one interrupt at completion. Far less CPU load — but more setup, and the memory must be DMA-mapped. The Microchip board does not use this path (the PIO_MODE quirk disables it).

The ring model

RingWhat lives in it
Command ringCommand descriptors the HW will execute (driver writes, HW reads)
Response ringCompletion status the HW writes back
IBI status ringOne entry per IBI event chunk
IBI data ringA pool of fixed-size chunks holding IBI payloads

Pointers are tracked in RH_RING_OPERATION1/2: an enqueue pointer (driver advances when adding work) and a dequeue pointer (hardware advances when finishing). When they differ, there's work in flight.

Key functions

FunctionRole
hci_dma_init / hci_dma_init_rhDiscover how many rings the HW offers, dma_alloc_coherent the rings, program their base addresses, enable them.
hci_dma_queue_xferMap each buffer for DMA, write descriptors at the enqueue pointer, advance it. Marks the last with "Interrupt On Completion."
hci_dma_xfer_doneOn the completion IRQ, walk from done-pointer to the HW dequeue pointer, match responses to transfers by TID, complete each.
hci_dma_dequeue_xferAbort: stop the ring, overwrite the pending descriptor with a no-op, restart.
hci_dma_process_ibiReassemble an IBI payload that may wrap around the chunk ring, copy into a slot, hand it up.
hci_dma_irq_handlerFor each ring, read RH_INTR_STATUS and dispatch: IBI ready, transfer complete/error, ring-op done, abort, ring-full.
Why DMA IBI needs a copy. Comment in the code: a payload can span chunks that wrap from the end of the ring back to the start, and upper layers may release chunks out of order — so the driver just memcpys into a discrete slot. Zero-copy isn't worth the complexity for typically-tiny IBI payloads.

cmd_v1.c — the short notepad HCI 1.0 / 1.1

32-bit command descriptors

drivers/i3c/master/mipi-i3c-hci/cmd_v1.c · implements mipi_i3c_hci_cmd_v1
A "command descriptor" is the order ticket the hardware reads. Its job is to translate a high-level request ("read 4 bytes from the device at address 0x12 at SDR speed") into the exact bit pattern the silicon expects. cmd_v1 packs this into two 32-bit words (sometimes with the data piggy-backed inside). This is the model the Microchip IP uses.

The five command "types"

TypeLetterUsed for
Address AssignmentADAA — handing out dynamic addresses
Immediate Data TransferITiny payloads (≤ a few bytes) stuffed into the descriptor — no separate data buffer
Regular Data TransferRNormal reads/writes with a data buffer
ComboCA write-then-read in one go (e.g. register address + read)
Internal ControlMDriver/HW housekeeping

The prep_* methods (what core.c calls)

MethodBuilds a descriptor for…
prep_cccA Common Command Code (broadcast or directed)
prep_i3c_xferA private I3C read/write — picks the SDR speed mode from the bus SCL rate
prep_i2c_xferA legacy I2C read/write — picks FM vs FM+ from the i2c rate
perform_daaThe full DAA loop (section 3)
Mode & rate selection. The code maps the configured SCL rate to an I3C SDR mode (SDR0–4) or I2C mode (Fm/Fm+). That choice ends up as bits in the descriptor telling the hardware how fast to clock this transfer.

cmd_v2.c — the long notepad HCI 2.0

64-bit command descriptors (the "Unified" command)

drivers/i3c/master/mipi-i3c-hci/cmd_v2.c · implements mipi_i3c_hci_cmd_v2

Same four prep_* methods, same vtable shape — but the descriptors are wider (four 32-bit words) and the format is the v2.0 "Unified Data Transfer Command." core.c picks this automatically when HC_CAP_CMD_SIZE says 64-bit.

What's similar to v1

  • Tiny writes (≤5 bytes) are stuffed into the descriptor as "immediate data bytes" (IDB) — no buffer needed.
  • Speed/mode still chosen from the bus rate via get_i3c_rate_idx/get_i2c_rate_idx.
  • Same ROC/TOC completion flags.

What's different

  • One unified command type instead of A/I/R/C/M letters.
  • DAA returns the ID as read-data of the address command itself — no DCT walk needed (contrast with cmd_v1).
  • Header explicitly warns the v2.0 spec "is still in flux" — expect change.
Why have both files? This is the payoff of the vtable design: core.c never branches on version in the hot path. It calls hci->cmd->prep_i3c_xfer() and the right notepad fills the ticket. Adding a hypothetical v3 would mean a new cmd_v3.c — zero edits to core.c's transfer logic.

dat_v1.c — the seating chart (Device Address Table)

In-hardware table mapping a slot → a device address & flags

drivers/i3c/master/mipi-i3c-hci/dat_v1.c · implements mipi_i3c_hci_dat_v1
The DAT is the master's address book, living in hardware registers. Each row (entry) holds one device's address plus behaviour flags (is it I2C? reject its interrupts? expect an IBI payload?). When core.c wants to talk to a device, the command references a DAT index (row number), and the hardware looks up the real address there. A software bitmap (DAT_data) tracks which rows are free.

The operations

MethodDoes
initValidate the table is in register space & 8-byte entries, allocate the shadow array + free-slot bitmap, zero every entry.
alloc_entry / free_entryFind/release a free row (via the bitmap). New rows default to "reject SIR & MR" (ignore this device's interrupt/mastership requests until told otherwise).
set_dynamic_addr / set_static_addrWrite a device's address into its row (with the odd-parity bit for dynamic addresses).
set_flags / clear_flagsFlip per-device behaviour bits (I2C_DEVICE, IBI_PAYLOAD, SIR_REJECT…).
get_indexReverse lookup: given a dynamic address, find its row.
restoreAfter a power-cycle/resume, rewrite every shadow entry back into hardware.
Why a shadow copy in RAM? The struct keeps a software mirror (hci->DAT[]) of every entry. Reads come from the mirror (fast, and survives suspend); the restore op replays the mirror into hardware on resume — which is exactly what core.c's rpm_resume calls.

dct_v1.c — the guest book (Device Characteristics Table)

Where DAA results land

drivers/i3c/master/mipi-i3c-hci/dct_v1.c · implements mipi_i3c_hci_dct_v1

The smallest file. During DAA the hardware writes each responding slave's identity into the DCT. This file's one job is to read an entry back out: read_entry() pulls the four words of a DCT row and unpacks them into the 48-bit PID, the DCR, and the BCR.

DAT vs DCT — don't mix them up. The DAT is write-mostly by software: "I decide device X lives at address Y." The DCT is write-by-hardware, read-by-software: "the bus told me a device with this ID showed up." DAA fills the DCT; software then copies the useful bits into the kernel's device model and assigns a DAT slot.

ext_caps.c — reading the kitchen's posted capabilities

Walk the optional-feature linked list in MMIO

drivers/i3c/master/mipi-i3c-hci/ext_caps.c
Extended capabilities are an optional-features menu the hardware posts in its registers. Standard registers are always there; everything beyond is described as a linked list: each block starts with a header (an ID byte + a length), and "next block = current + length". The driver walks this list once at probe, runs a small parser per ID it recognises, and skips ones it doesn't.

What the parsers do

Cap IDParserEffect
0x01hardware_idRead vendor MIPI/version/product IDs. NXP → set the RAW_CCC quirk.
0x02master_configConfirm the IP supports master mode (else bail with -EOPNOTSUPP).
0x04 / 0x08xfer_modes / xfer_ratesLog the supported transfer modes and data rates.
0x05auto_commandRemember the auto-command register block for later.
0x0cdebugStash the debug register pointer.
0xc0–0xcfvendor-specificDispatched to a per-vendor parser (e.g. NXP FPGA reset).
This is "self-advertising hardware" in action. Instead of the driver hard-coding "this chip has feature X," it discovers features at runtime by reading what the silicon declares — the core idea that lets one HCI driver serve many vendors.

hci_quirks.c — AMD house rules

Pre-existing vendor quirks (the pattern the Microchip file copies)

drivers/i3c/master/mipi-i3c-hci/hci_quirks.c

This file predates the Microchip work and shows the established pattern: a quirk is just a small function, gated by a HCI_QUIRK_* bit, that pokes vendor-specific registers core.c wouldn't otherwise touch.

FunctionGated byWhat it does
amd_set_od_pp_timingHCI_QUIRK_OD_PP_TIMINGWrite hard-coded constants (0x00cf00cf OD, 0x00160016 PP) tuned for AMD's 9 MHz, plus a max TX-hold-time bit.
amd_set_resp_buf_thldHCI_QUIRK_RESP_BUF_THLDClear the response-buffer threshold field so a single response triggers "ready."
"OD" and "PP" are the two electrical phases of I3C signalling. Open-Drain (OD) is the slow, robust phase used for addressing and legacy I2C (the line is pulled up by a resistor). Push-Pull (PP) is the fast phase used for I3C data (the driver actively pushes both high and low). Each needs its own SCL high-count/low-count timing, which is what these registers hold.

hci_quirks_mchp.c — Microchip house rules your work

Compute SCL timing from the live gclk rate instead of hard-coding

drivers/i3c/master/mipi-i3c-hci/hci_quirks_mchp.c

The key difference from AMD: AMD writes fixed magic numbers; Microchip computes the timing from the actual gclk rate (125 MHz) and the configured bus rates, so the same code stays correct if the clock changes.

mchp_cfg_od_pp_timing()

core_rate = clk_get_rate(hci->gclk);   // 125 MHz
/* Push-Pull: high count from max SCL-high time, low count fills the rest */
hcnt = DIV_ROUND_UP(THIGH_MAX_NS * core_rate, NSEC_PER_SEC) - 1;
lcnt = DIV_ROUND_UP(core_rate, scl_rate.i3c) - hcnt;
reg_write(HCI_SCL_I3C_PP_TIMING, HCNT(hcnt) | LCNT(lcnt));
/* Open-Drain: derived from the I2C rate */
lcnt = DIV_ROUND_UP(core_rate, 2 * scl_rate.i2c);
hcnt = DIV_ROUND_UP(core_rate, scl_rate.i2c) - lcnt;
reg_write(HCI_SCL_I3C_OD_TIMING, HCNT(hcnt) | LCNT(lcnt));
reg_write(HCI_BUS_FREE_TIMING, FREE(lcnt));   // bus-free idle time
What "hcnt/lcnt" mean. The SCL clock is generated by counting source-clock ticks: hold it high for hcnt+1 ticks, low for lcnt ticks. With a 125 MHz source each tick is 8 ns. So to make a 12.5 MHz I3C clock you need ~10 ticks per period, split into a high part and a low part. The formulas just turn "nanoseconds I want" into "ticks to count."

mchp_cfg_resp_buf_thld()

Clears the response-buffer-threshold field in QUEUE_THLD_CTRL (gated by HCI_QUIRK_MCHP_RESP_BUF_THLD) so the controller signals "response ready" after one response — the Microchip-owned twin of AMD's amd_set_resp_buf_thld.
